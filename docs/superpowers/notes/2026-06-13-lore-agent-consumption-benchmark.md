# lore agent 消费基准 —— 冷启动对照测试

> 2026-06-13 · 方法论 + 数据沉淀。被测对象脱敏为「项目 P」：一个真实生产项目，约 5 个管线模块 + 1 个共享层，代码与文档均在子目录。

## 方法

零上下文 subagent，同题双盲两组、信息源互斥：
- **wiki 组**：只许用 lore wiki（`ask.js` 检索 + Read 合成页），禁读源码/git。
- **source 组**：只许读源码 + git，禁读 `.lore/`、docs、README。

三轮 × 每轮 3 题 = 9 题。题型按「lore 的不同主张」分布：架构/数据流（R1）、某子管道入口与过滤全集（R2）、某生成途径与后处理分层（R3）。正确率由持有 ground truth 的主控交叉核对。

## 结论

1. **「测试暴露缺口 → 补清单型事实 → wiki 追平/反超」闭环成立**。R2/R3 在更早一轮（补录前）wiki 曾漏答「子管道三入口」「生成途径全表」；把这些**清单型事实**（入口全景 / dispatch 总表 / 跳过原因全集）补成表格进 wiki 后，本轮 wiki 不仅答全，R3 的「途径总表 + 后处理四层」比 source 组更结构化完整。**散在多文件的同主题清单是 wiki 相对源码的最高价值内容形态**（源码组要 17-21 次工具调用拼出来的，wiki 一张表）。

2. **效率优势真实但不均匀**：R2 wiki 省 55% token、1/3 工具调用碾压；R3 持平；**R1 wiki 反而更贵**（102k > 83k）。根因——wiki 组用 `ask.js + Read 整页`，读到的合成页含**长决策史物化区**（页底 `## Decision history` 折叠的 journal 原子可达几十 K），读架构/机制却连决策史一起烧。**可操作优化**：消费「为什么之外」的问题时应剥掉决策史物化区（MCP `lore_page view=agent` 方向），决策史按需单取。

3. **摘要层 vs 实现层是设计取舍，不是 bug**：source 组答得出行级细节（具体阈值、指纹清单、特判分支），wiki 是摘要层到不了。真实使用形态是 **wiki 先建框架/给锚点 → 卡细节再按锚点下钻源码**——wiki 页内的 `func @ file` 锚点正是这条路径的导航。纯 wiki 或纯源码都不是最优，混合才是。

4. **长工具链有可靠性税**：source 组（17-21 次工具调用）一轮里挂了一个（偶发 skill 冲突 / API 错误，0 产出需重跑）；wiki 组（6-7 次）零故障。工具链越短越稳。

## 待优化项（第一轮产出）

- **决策史物化区按需化**：读厚页不应连决策史一起返回（R1 贵的根因）。
- **agent 消费纪律 + 混合范式固化**：让装了 lore 的 agent 默认走「wiki 建框架 + 锚点下钻源码」，而非靠提示偶尔想起。

---

## 第二轮（优化后复测）—— 上述待优化项落地后同题重测

落地了三处优化：① `agentView`（`view=agent`）剥决策史物化区；② `ask.js` CLI 直接返回命中节切片内容（不再「只给路径 → 读整页」）；③ resident 文案教「ask 切片够答就别读整页、读页跳决策史」。wiki 组按优化链路重跑同样 9 题。

### 复测结论

1. **R1 反转**——优化前唯一 wiki 输给 source 的轮（102k > 83k），复测 **55.2k < 95.9k**。根因（读整页烧决策史物化区）被「剥决策史 + ask 切片」精准根治。待优化项闭环验证成功。
2. **「0 整页 Read」成主流**：R2/R3 全程不读整页（切片够答），R1 仅 1 页且跳决策史——决策史物化区基本不再进 context，这就是省下来的 token。
3. **wiki vs source 差距从省 19% 拉大到省 62%**（148.3k vs 386.4k）。wiki 链路变轻 + source 组读更细（R3 source 6900 行）两头拉开，正确率仍 9/9——**省 token 零正确性损失**。
4. **新发现的方法论噪音**：「禁读 wiki 外」的对照实验里，subagent 会被 lore 自己注册的 `lore:ask` skill 语义提示干扰、去「考虑用 skill」而非直接干活（两轮各摆烂一次，需重跑）。真实使用中用 skill 是好事；但对照测试需在 prompt 显式「不要调用 skill，直接用工具」。
